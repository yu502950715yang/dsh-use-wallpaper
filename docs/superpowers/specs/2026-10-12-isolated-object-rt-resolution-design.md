## 1. 概述

**问题**：壁纸「魔兽之门」`1922570576` 在 DSH 里比桌面 Wallpaper Engine 明显糊。用户报告的原始现象，已在用户截图上量化复现。

**根因（实测锁定，非推断）**：带 `effects` 的对象不走直渲，而走**隔离路径** —— 内容 → 对象 RT → 效果链（多 pass）→ 合成 quad → 屏幕。本仓库把对象 RT 尺寸定为**屏占位 1×**（`object-range.objectRtSize`，§5.15 ②），而桌面 WE 用的是**源纹理原生尺寸**（本壁纸 5000×2400，≈屏占位的 2.4× 超采样）。在 1× 上：

1. 5000×2400 源图先被缩小 2.4×（GPU mip 链三线性，未设 anisotropy）⇒ 最高频被削；
2. 效果链的每一遍（godrays 合成、waterripple 的 UV 扰动 = 双线性重采样）都在这个屏幕级网格上执行 ⇒ 每遍再加一点亚像素模糊，合成 quad 又是 1:1 贴回 ⇒ **模糊不可逆**。

桌面在同一串 pass 上跑 5000×2400，最后只做一次缩放到屏幕，单遍重采样模糊被缩小 2.4 倍 ⇒ 看不出来。

**影响面**：全库 33 张 scene 壁纸中 **19 张**含「带 effects 的 image 对象」，共 **65 个**对象走这条路径（其中**只有 21 个是铺满整屏的背景**，其余是局部贴片）。

**本设计做什么（出厂口径 = 逐对象，R37 裁决）**：**每个**带 `effects` 的隔离 image 对象都按 §3.1 公式 `max(屏占位长边, min(源纹理长边, 4096))` 把 RT 分辨率提上去，**不设「满屏」门槛**；「铺满整屏」只用于 **MSAA 分型**（满屏对象关 MSAA，其余保留，见 §3.2）。用省下的显存 + 预算守卫（§3.5）付账。

> **命名说明（R37）**：本文档全书用「方案 A′」指**出厂采用的逐对象口径**（§3.1）；而 §2.5 显存档位表里的
> 「方案 A′ / 方案 A」是**立项前实验臂**的旧称（分别为「只动满屏对象」/「改全部对象」），**同名不同义**。
> 出厂实现的代价对应旧称里的「方案 A」那一档，见 §2.5 与 §2.4 末的出厂实测。

## 2. 事实基础（全部为本轮实测）

### 2.1 现象定位：不是 DSH 的锅

- DSH 截图里**它自己的 UI 文字**边缘锐度 ≈ 原生（"最大梯度/对比度" 比值 ≈ 1.0）⇒ 整个窗口没有被 OS/DPI 拉伸；
- 同一张截图里**壁纸的文字（时钟）层**与桌面几乎同锐，而**背景**明显更软 ⇒ 不是整块 canvas 被放大（即画质档位不是 0.75/0.5，canvas 缓冲与物理像素 1:1）；
- 用项目自带 harness 真机渲染同一张壁纸（1600×900、dpr=1，**完全脱离 DSH**）与桌面 WE 截图配准（NCC≈0.99）逐块比较：**108 个有效块锐度比中位数 0.54** ⇒ 糊是插件自身渲染路径的性质。

### 2.2 单张 A/B：分辨率是主因，MSAA 无影响，效果链只占小头

harness 1600×900 / dpr=1，指标 = 逐块「梯度/对比度」比，桌面 WE = 1.00：

| 组 | 变化 | 对象 RT | 锐度比 | Laplacian 比 |
|---|---|---|---|---|
| 桌面 WE | 参考 | 5000×2400（原生） | 1.00 | 1.00 |
| A | 现状 | 1875×900 | 0.55 | 0.15 |
| B2 | 只关 MSAA（4→0） | 1875×900 | 0.56 | 0.15 |
| B3 | 只摘掉 3 条效果链 | 1875×900 | 0.67 | 0.25 |
| B6/B7 | RT 1.5×（±mipmap） | 2813×1350 | 0.73 | 0.32 |
| B1 | RT 提到 4096 收口 | 4096×1966 | 0.87 | 0.61 |
| B5 | 4096 收口 + mipmap | 4096×1966 | 0.88 | 0.61 |

### 2.6 代码事实

- `object-range.objectRtSize()`：`RT 像素 = |世界尺寸| × 屏幕密度`，等比收口 `OBJECT_RT_MAX = 4096`；注释明确「WE 的对象 RT = 纹理真实尺寸…本口径取 1:1（最小无损）」。
- 两处调用必须**同源**：`three-renderer` 挂载期（isolate 表）与 `object-effects.onViewportResize`（resize 重挂）—— §5.15 ② 的教训（口径不一致会让整层模糊）。
- `threejs-player.attachIsolated()`：`new THREE.WebGLRenderTarget(rtW, rtH, { samples: 4 })` 硬编码 MSAA 4×；合成 quad 用 `createCompositeGeometry(worldW, worldH, camW, camH)`，局部相机范围 = **未钳制世界尺寸**。
- `tex-loader`：`.tex` 纹理 `minFilter = LinearMipmapLinearFilter` + `generateMipmaps = true`、`magFilter = Linear`，**未设 anisotropy**；视频纹理（flags bit5）走 `videoTextureFromMp4`，尺寸**异步**；精灵表（flags bit2）走 `sprite` 分段。
- 仓库自测记录：背景隔离内容是一整块铺满 RT 的 quad，`samples=0` 与 `samples=4` **逐像素完全相同（MAD = 0.0000）**。

## 3. 设计（方案 A′）

### 3.1 尺寸策略

对**每个隔离对象**计算：

```
occLong   = max(|worldW|, |worldH|) × 屏幕密度        // 现状口径（屏占位）
srcLong   = 源纹理长边（.tex mip0 的 image 尺寸；未知则视为 0）
targetLong = max(occLong, min(srcLong, OBJECT_RT_MAX))  // 只升不降（护栏）
RT        = 世界尺寸 × (targetLong / max(|worldW|,|worldH|))，等比、按 targetLong 归一到 4096 收口
```

要点：

- `max(occLong, …)` 是**不回退护栏**：源纹理比屏占位小的对象（全库 1 例）保持现状不动。
- 与 WE 的差别仍然存在（WE 不设 4096 上限，GTR 会用 7430×4147）；本设计取「纹理原生 ∩ 4096」，因为 A/B 显示 4096 收口已拿到 0.87（桌面 1.00），再往上性价比极差且显存风险高。
- 局部相机范围仍 = **未钳制世界尺寸**（§5.15 ② 的不变量不变），只是像素网格变密。
- 密度基准仍由调用方从主相机同一套 cover 语义取得；**挂载期与 resize 期必须调同一个纯函数**。
- 返回前**逐轴 clamp 到屏占位**（`max(occ.width, max(1, round(…)))`，而非只看长轴）：预算收窄到极限（`budgetScale = 1e-4` 兜底）时，
  长轴 round 进位、短轴 round 舍去会让短轴比屏占位少 1 px ⇒ 只保证「长轴 ≥ occLong」的护栏不够（2026-10-12 整支审查 I1）。

### 3.2 MSAA 分型

- **铺满整屏**（`worldW ≥ 0.98 × 场景宽` 且 `worldH ≥ 0.98 × 场景高`）⇒ `samples: 0`：这块 RT 内只有一张盖满的 quad，没有轮廓边，MSAA 结构性无效（实测 MAD=0.0000），省下的 24 B/px（28 B/px「无 MSAA」vs 52 B/px「MSAA 4×」模型）用来买分辨率。
- **其余对象**（贴片 / 粒子 billboard）⇒ 保持 `samples: 4`：它们有真实几何边，MSAA 有用。
- 判定在 `attachIsolated` 内用 player 自己的 `sceneWidth/sceneHeight` 完成，不额外传参。

### 3.3 合成采样（mipmap）

RT 一旦大于屏占位，合成那一步就是**缩小**采样。此时给隔离 RT 开 `generateMipmaps + LinearMipmapLinearFilter`；RT 未放大时保持现状（不改既有行为）。实测该开关对锐度无影响（0.87→0.88），纯粹防高频闪烁/走样。

### 3.4 回退（源尺寸未知）

按优先级取源尺寸，取不到就**回退屏占位**（绝不建 1×1/NaN 的 RT）：

1. `.tex` 普通图像：`tex.image.width/height`（mip0 image 尺寸，**不是** `textureWidth/Height` 的 NPOT padding 尺寸）；
2. 视频纹理（flags bit5）：`videoWidth/videoHeight` 就绪前 → 回退屏占位（是否在就绪后重设 RT 留作后续，见 §7）；
3. 精灵表（flags bit2）：**不采用**图集尺寸，回退屏占位；
4. 粒子对象（无纹理，尺寸由 `distanceMax × scale` 决定）：不适用本策略，保持现状口径；
5. 任何异常（NaN/0/缺失）→ 回退屏占位。

### 3.5 显存预算与降级

新增纯函数 `fitIsolatedBudget(items, density, budgetBytes?, bytesPerPx?)`：按每像素字节模型估算隔离 RT 总占用，超预算时**等比下调 targetLong**，下限 = 各对象的屏占位（即最坏退回现状，不会比今天更糊）。预算取常量（v1 不新增设置项 UI，见 §6）。

### 3.6 context lost 回退

监听 `webglcontextlost`：`preventDefault()` 停掉播放器，切回该壁纸的 preview 图（`layer.showImage(previewUrl)`），并给一次可辨识的 `console.warn`。理由：RT 变大后显存压力上升，而现状下 context lost 就是**空白画面**，比「糊」严重。

### 3.7 与既有硬约束的关系

| 约束 | 本设计的态度 |
|---|---|
| §5.15 ②（RT = 屏占位；相机范围 = 完整世界尺寸） | 相机范围不变；**尺寸口径改为「≥ 屏占位」**，并把「只升不降」写成护栏（本次修订 §5.15 ② 的表述） |
| §5.21（同一把尺子，挂载/resize 同源） | 两处都调用同一个纯函数；单测锁「改密度不改变映射」 |
| §5.22（渲染进 RT 透明清屏） | 不变（仍走 `rt-render.ts` 唯一入口） |
| §5.11（帧内不得建 RT） | RT 只在挂载期/重挂期建，尺寸变更走既有 `resizeObjectRT` |
| §7.30（Glow 开启时无 MSAA） | 与本设计正交；本文只改**对象** RT 的 MSAA |

## 4. 验收判据（可执行）

1. **单测**（`npx vitest run tests/object-range.test.ts` 等）：
   - `max(屏占位长边, min(源纹理长边, 4096))` 三态：源纹理更大 → 提升；源纹理更小 → **不变**（`1968789468` 那例）；源纹理未知 → 不变；
   - 4096 等比收口（不逐轴截断，aspect 不变）；
   - 预算超限 → 等比下调且不低于屏占位；
   - 挂载期与 resize 期结果一致（**单测口径**：同一纯函数、同一输入 ⇒ 同一输出；两期预算输入集合不同，见 `AGENT.md` §7.36②）；
   - 满屏对象 `samples: 0`、非满屏对象 `samples: 4`、RT 放大时 mipmap 开。
2. **e2e 渲染**（`e2e/verify/verify-isolated-rt-sharpness.mjs`，复用 harness 与分块指标；**实际采用的口径**）：
   - **结构性判据**（承重，**素材侧独立算出**、不比对参考图）：RT 长边 === 独立算出的期望（`max(屏占位长边, min(源纹理长边, 4096))`）、`rtPx ≥ 屏占位像素`（只升不降）、满屏背景 `samples=0` / 其余 `samples=4`、mip 与「RT 长边 > 屏占位长边」一致；
   - **运行期量**（同属判据，但不是素材侧算出来的）：FPS ≥ 30、无失败类告警 —— 判据清单以脚本内 `add()` 为准（结构性 4 + 遮罩槽 2 + 运行期 2 + 页面就绪 / 视口与 DPR 一致 / 素材侧非空 / `__isoInfo` 可读 / 隔离集合一致 5 + 锐度 2，另有锐度可算性前置检查），每类按对象展开；

## 5. 风险与未验证项（如实）

- **FPS 已采基线（计划 Task 1，`--gpu`）**：`--id=1922570576` → `{"fps":60,"frames":301,"ms":5016}`；`--id=3743126786` → `{"fps":60.1,"frames":301,"ms":5004}`。渲染器 `ANGLE (NVIDIA, NVIDIA GeForce RTX 3060 …, D3D11)`、WebGL 2.0 ⇒ 真 GPU，非 SwiftShader。
  **局限**：两条数字都贴在本机 60 Hz vsync 天花板（`CurrentRefreshRate 60`）上，该探针只能回答「有没有跌破 60」，**测不出 60 以上的余量**；因此 FPS ≥ 30 判据只能当「地板」用，低端 GPU / 4K 屏的余量仍未覆盖。
- **效果观感变化**：RT 纹素密度变大后，以纹素为单位的参数（godrays 高斯 `blurscale`、downsample2 级数）相对屏幕尺度变小 ⇒ 光柱/模糊会变（方向上更接近 WE，因为它纹素密度 = 源纹理）。锐度指标测不出这个，只能逐张目视；本轮已目视 4 张（GTR / Crimson / Subway / Orange），未覆盖其余 15 张。
- **切换峰值**：切壁纸时新旧 RT 可能并存，峰值≈两者之和（如 GTR 285 MB + 克西高达 601 MB）+ DSH 界面本身；预算护栏只能约束稳态，峰值需实测。
- **显存数字是解析估算**（每像素字节模型），非 GPU 实测；±20% 量级误差。
- **视频纹理重设**：v1 只做「就绪前回退屏占位」，不做「就绪后重设 RT」（`2911105183` 有 3 个视频对象）——该壁纸的实际收益会低于其纹理应有的水平。
- **R31：`lib/` 落后于 `src/`（环境事实，发布前必做）**：e2e 脚本在现场用仓库自己的 `tsc` 编译 `src/` 验收（写下时 git 跟踪的 `lib/client/object-range.js` 里没有 `isolatedRtSize`；**已在 `22e6fb4` / `d7f6ec3` 重建后包含**，本句仅为当时依据）⇒ 验的是「src 的编译产物」，**不是**入库的 `lib/`；发布前必须 `npm run build` + `npm run build:client`，否则 DSH profile 里跑的仍是旧实现。
- **R32：粒子 / 精灵表没有真实样本**：e2e 清单的 29 个隔离对象全是 image / background（扩清单前 5 张为 26 个；**A2 扩到 8 张后仍是 29 个全 image**），**粒子与精灵表各 0 个** ⇒「粒子恒 `samples=4`、精灵表回退屏占位」只有单测覆盖（A2 已把「源未知 ⇒ 回退屏占位」钉进 oracle 的 `--selftest`；粒子 `samples=4` 那条仍在 `analyseWallpaper` 内联、未进自检）；锐度判据的余量也偏薄（逐块中位数最低 **1.10** vs 阈值 1.05）。

## 6. 非目标

- **不做 WE 口径**（RT = 纹理原生、不设 4096 上限）：中位 +320 MB、最坏 +1797 MB，换不到相应锐度（§2.5）。
- 不改纹理过滤/anisotropy（对正对屏幕的背景 quad 不是杠杆）。
- 不改效果链语义（不改 pass、mask、混合、具名 RT 规则）。
- 不改非隔离对象的渲染路径（粒子、文字层、直渲背景）。
- v1 **不新增设置面板控件**（避免动被测试锁定的 DOM 钩子，§5.39）；预算走常量，档位化留作后续。
