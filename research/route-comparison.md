# Scene 播放技术路线对比（2026-08-19）

- 背景：外部建议"用 RePKG 解包 scene 素材 → 网页技术手工重实现动态效果"。本文基于全库实测数据对比两条路线，供决策。
- 前置证据：`research/scene-play-research.md`（24 壁纸实测判定表、根因清单、引擎头文件对照）

## 1. 两条路线定义

- **路线 A（现状，运行时解析渲染）**：DSH 插件内直接解析 scene.pkg（scene.json/粒子/材质/效果链/tex），Three.js WebGL 实时渲染。**已实现并运行**：24 壁纸 0 黑屏、15 动态。
- **路线 B（外部建议，RePKG 解包重实现）**：用 RePKG/RePKG-GUI 把 scene.pkg 解包为图片/JSON/视频素材，为**每个壁纸**手写 HTML/CSS/JS/WebGL 动画。

## 4. 对比矩阵

| 维度 | 路线 A（运行时解析） | 路线 B（RePKG 重实现） |
|---|---|---|
| 动态语义保真 | ✅ 粒子物理/效果链 shader/音频均在浏览器执行 | ❌ 解包只得静态素材，动画逻辑全要手写 |
| 覆盖面 | ✅ 24/24 解析成功（0 黑屏 15 动态） | ❌ 逐壁纸制作，D 类 11 个混合壁纸工作量爆炸 |
| 扩展性 | ✅ 新壁纸/库更新自动支持 | ❌ 每次更新需重新解包 + 重做 |
| 成本 | ~10 人日 | ~150+ 人日 |
| 维护 | 单一引擎，集中修 | 24 个独立网页，分散维护 |
| 视觉上限 | 受 shader 兼容性制约（瓶颈已定位，修复路径明确） | 理论可逐壁纸调优到接近原版，但成本线性增长 |
| 风险 | 低（已运行，增量修复） | 高（工具链依赖 RePKG 维护；重实现质量参差；半途而废风险） |
| 适用场景 | **DSH 内播放全库壁纸（我们的目标）** | 把**单个**壁纸做成独立展示页 |

## 5. 结论与建议

1. **路线 B 的建议对"不了解 WE 格式、只想做单个壁纸网页版"的人合理，但对"DSH 插件播放全库 24 个 scene 壁纸"的目标是错误路线**：成本高 15 倍、不可扩展、且重实现仍要写粒子模拟与 shader 执行（正是路线 A 已有的能力）。
2. **路线 A 的瓶颈不是格式解析（已 100% 健康），而是效果链 GLSL 兼容**——根因全部定位，且本机 WE 客户端引擎头文件（common_composite.h 等）已提供权威实现，修复是"照着写"，风险低、收益大（vhs/clouds/blur_combine 编译失败直接修复）。
3. **RePKG 在本项目中唯一合理用途**：调试辅助（.tex → PNG 核对纹理）、单个壁纸的独立展示页（非本项目目标）。
4. **建议**：维持路线 A，按根因清单实施（P0-1 → P0-3 → P0-4 → P1-2 → P1-1 → 其余）。
